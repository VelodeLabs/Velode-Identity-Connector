# Security Guide

What the connector protects, and what an application that uses it must still do.
Report vulnerabilities as described in the [security policy](../SECURITY.md).

## Trust Model

Velode Identity authenticates users and decides whether they may enter the application. The connector carries that
decision to the application; the application owns roles, permissions and its own data.

The connector holds one secret of its own: the **connection key** that authenticates the application to Identity.

- It is 32 random bytes, generated by the connector. Nobody copies it or puts it in configuration.
- It is stored in the application's database, in the `velode_identity_connection` table (or a custom
  `ConnectionStore`). Anyone who can read that table or its backups can call Identity as the application, so protect
  them like other credentials.
- It is replaced every 30 days by default (`velode.identity.key-rotation`). Replicas share the replacement atomically.
- An administrator who disconnects the application in Identity revokes the key at once; the connector then asks to be
  approved again with a new one.

The approval code shown in the application's log, such as `4F7-A92`, is not a secret: administrators compare it
with the panel. The connector never logs the key, flow secrets or session tokens.

## Transport

`velode.identity.url` and `velode.identity.app-url` must use `https`, or the application does not start.
Plain `http` is accepted only for `localhost`, `127.0.0.1` and `[::1]` during development. The connector never follows
redirects from Identity, so the key is only ever sent to the configured address.

## Browser Sessions

After sign-in the application's session token lives in the `velode_identity_session_token` cookie: `HttpOnly`,
`Secure`, `SameSite=Lax` and scoped to the application's context path. `currentUser` and `verify` ask Identity on every
call, so a user who is disabled or loses access is refused on their next request.

Signing out at `/velode-identity/logout` clears the application's cookie only; the user's Identity session remains.
Sign-out requests started by another site are refused.

## Sign-In Endpoints

**Redirect sign-in** (`/velode-identity/login` and `/velode-identity/callback`):

- Each sign-in carries a fresh 192-bit `state`, bound to an `HttpOnly` cookie for ten minutes and compared in constant
  time, so another site cannot complete a sign-in in the user's browser.
- `returnTo` only accepts paths inside the application; anything else returns the user to `/`.
- The callback is never cached and sends no `Referer`, so the one-time code does not leak.

**The application's own sign-in page** (`/velode-identity/flow/*`):

- Steps accept only `application/json` bodies up to 8 KB, which ordinary HTML forms cannot send.
- A `POST` whose `Origin` differs from `velode.identity.app-url`, or whose `Sec-Fetch-Site` is not `same-origin`, is
  refused with `403 CROSS_ORIGIN`.
- The flow lives in an `HttpOnly` cookie for 20 minutes; page scripts never see it.
- A session is set only after Identity confirms that the token it issued belongs to the same user.
- Identity applies Turnstile, rate limits and lockouts to the browser's address.

## What The Application Must Do

- **Serve the application over HTTPS** at the origin set in `velode.identity.app-url`.
- **Trust forwarded headers only from your own proxy.** Identity limits sign-in attempts by the address the connector
  reports. Behind a proxy, set `server.forward-headers-strategy` and make sure clients cannot reach the application
  directly, or anyone could send a forged `X-Forwarded-For` and avoid the limits.
- **Protect the connection table** and its backups as credentials, and give the database account only the access it
  needs.
- **Authorize every request.** The connector does not populate Spring Security's `SecurityContext`. Check
  `currentUser` on every protected route and apply the application's own roles.
- **Protect the application's own state-changing routes against CSRF.** `SameSite=Lax` stops most cross-site
  requests, but not those from sibling subdomains. With Spring Security, keep CSRF protection on for the application's
  routes; exclude `/velode-identity/flow/**` or send the CSRF header with those requests.
- **Keep the connector current.** Only the latest minor version receives security fixes.

## Checklist

- [ ] Both `velode.identity.*` addresses use `https`.
- [ ] `server.forward-headers-strategy` matches the deployment, and only the proxy can reach the application.
- [ ] `/velode-identity/**` is permitted; every other route checks the user and the application's permissions.
- [ ] CSRF protection covers the application's own state-changing routes.
- [ ] The `velode_identity_connection` table and backups are restricted.
